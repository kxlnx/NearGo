> 答案以本项目实际代码为准；标「缺口」的表示当前实现不完整，面试时照实说。

## 〇、开场与真实性核验

1. **介绍一下这个项目。**
   答：NearGo 是一个到店点评系统，核心业务是「店铺浏览 + 优惠券秒杀」。主链路：请求先过限流 → Redis Lua 原子预扣（防超卖、一人一单）→ RocketMQ 异步下单（削峰、幂等）→ 延迟消息超时关单 → XXL-JOB 对账兜底；读侧有逻辑过期和 Caffeine/Redis 两级缓存。我在黑马点评基础上扩展了异步下单、对账、限流和两级缓存。

2. ⚠️ **这是黑马点评吧？哪些是教程的、哪些是你自己加的？**
   答：是，基于黑马点评二次开发。教程原有：商铺缓存（逻辑过期）、基础秒杀 Lua、一人一单、Redisson 锁、签到/关注/点赞；我的扩展：① reservation 流水 + XXL-JOB 对账闭环；② MQ 异步落库与幂等强化；③ 延迟关单 + 状态条件更新；④ 注解式滑动窗口限流；⑤ Caffeine 两级缓存。主动区分，别含糊。

3. **项目规模和运行环境？**
   答：核心表 4 张（tb_shop、tb_voucher、tb_seckill_voucher、tb_voucher_order）；中间件 Redis、RocketMQ、XXL-JOB、MySQL；本地起中间件后 `mvn spring-boot:run`，应用端口 8081，执行器端口 9999。

4. **七点里哪点最难？**
   答：对账补偿。要收敛 Redis、MySQL、MQ 三方跨存储状态，还要处理重投限频、幂等、失败重试，是分支和边界最多的部分。

5. **哪一点设计得最巧？**
   答：reservation 流水。Lua 预扣时顺手写的一条 Hash，同时服务三件事：未落库重投的凭据、已取消释放的依据、正常落库后的销账对象。

6. **哪个知识点理解变化最大？**
   答：一致性。之前以为加锁/事务就能保证，做完发现分布式下只能接受短暂不一致，用幂等 + 消息 + 对账去收敛。

7. **有没有推翻重做的方案？**
   答：有。发送失败补偿最早是直接删资格回滚，后来改成幂等脚本（先 SISMEMBER 再决定是否回滚），防重复执行把库存加多。

8. **下一步最想优化什么？**
   答：跨实例缓存失效广播、补偿最大次数与告警、`(user_id, voucher_id)` 唯一索引、把对账在真实 Admin 上端到端验证。

9. **最不自信的地方？**
   答：XXL-JOB Admin 的跨进程调度、故障转移没有端到端验证；没有真实流量，压测只是本地单机。

10. **用三个词概括？**
    答：秒杀、异步削峰、最终一致。

## 一、业务场景题

1. **秒杀活动怎么创建？**
   答：运营调 `POST /voucher/seckill` → `addSeckillVoucher`：写 `tb_voucher`（券本体，type=1）、写 `tb_seckill_voucher`（库存/起止时间）、把库存预热到 Redis `seckill:stock:{id}`，最后删券列表缓存。

2. **券的完整生命周期？**
   答：创建（type 0 普通 / 1 秒杀）→ 上架（status=1）→ 用户秒杀 → 订单 1 待支付 → 支付回调 2 已支付 / 超时 4 已取消 → 后续 3 已核销、5 退款中、6 已退款（3/5/6 预留未实现）。

3. **用户参与秒杀的路径？**
   答：进店铺页 → `GET /voucher/list/{shopId}` 看券 → `GET /voucher/seckill/{id}` 看详情 → `POST /voucher-order/seckill/{id}`（需登录）→ 返回 orderId → 支付回调改状态。

4. **为什么要一人一单？**
   答：业务原因：限量营销，一人多单会被脚本/黄牛放大，破坏公平、加剧超卖与客诉，库存要尽量分给更多用户。
   怎么保证（分三层）：① 接入层 Lua：`SISMEMBER seckill:order:{voucherId} userId` 命中返回 2、不扣库存；未命中 `SADD` 入名单——查重、扣库存、记名单在同一原子脚本里；② 消费端：同一用户用 Redisson 锁串行 + `count(user_id, voucher_id)` 联合校验，已有订单直接返回；③ 失败归还：发送失败补偿、关单释放、对账释放都会 `SREM`，保证资格能还回去、用户可重新参与。
   缺口：没有 `(user_id, voucher_id)` 唯一索引，最终防线靠锁 + 校验，生产应补。

5. **为什么要超时关单？多久合理？**
   答：未支付订单一直占用库存，必须回收再卖。本项目演示用 1 分钟（延迟等级 5）；生产一般 15 分钟左右，按业务定。

6. **支付回调谁调用？真实流程？**
   答：真实业务是第三方支付异步通知商户服务端：验签 → 校验金额/订单号 → 幂等更新状态 → 返回成功。本项目简化为前端登录后调 `POST /voucher-order/pay/callback/{orderId}`，没有验签和订单归属校验（缺口）。

7. **核销/退款为什么没实现？**
   答：属于券后生命周期，需要店员权限、核销幂等、退款走支付渠道并要求资金/券状态一致；当前订单状态 3/5/6 预留未实现（缺口）。

8. **普通券和秒杀券业务区别？**
   答：普通券无库存与时间窗口限制（本项目未实现领取流程）；秒杀券有库存和活动时间，走秒杀链路（Redis 预扣 + MQ + 关单 + 对账）。

9. **券为什么绑店铺？**
   答：`tb_voucher.shop_id` 记录归属，券只能在其店铺使用；订单表没有 shop_id，绑定由券本身决定。

10. **库存从哪来？卖完怎么办？**
    答：运营建活动时填写并预热到 Redis；卖完 Lua 返回 1（库存不足），用户看到失败提示；运营可下架（status=2）。

11. **活动前/中/后做什么？**
    答：前：预热库存、压测、限流配置；中：盯盘、限流、对账；后：清理 `seckill:stock`（无 TTL）、下架券、数据汇总。

12. **业务上为什么要缓存？哪些页面最热？**
    答：店铺详情、券列表、秒杀详情都读多写少、热点集中；不缓存会直接打 DB。

13. **为什么允许 5~30 秒旧值？哪些不能？**
    答：券信息、店铺详情变化不敏感，短旧值可接受；库存、余额、支付状态等强一致数据不能（本项目库存实时读 Redis）。

14. **对账告警谁处理？损失是什么？**
    答：应由值班/业务处理；不一致可能导致资损（超卖/少卖）和客诉。本项目只告警 + 有限自动修复（缺口：无人接收告警）。

15. **秒杀成功但订单没落库怎么补偿用户？**
    答：对账扫 reservation：订单确实不存在就原 orderId 重投；重投不成继续兜（当前无最大次数），最终人工介入退款/补发（缺口）。

16. **限流为什么分用户/IP？**
    答：user 防同一账号脚本刷单；ip 防同一出口爬虫/批量请求；global 兜总量。

17. **大促流量特征？**
    答：瞬时尖刺（开抢几秒）、读多写少、热点集中，所以需要削峰 + 限流 + 缓存。

18. **3/5/6 状态业务含义？**
    答：3 已核销、5 退款中、6 已退款；预留未实现。

19. **重复下单的业务危害？**
    答：同一用户占多份库存、可能倒卖、加剧超卖与客诉，破坏营销公平。

20. **假失败业务上什么现象？**
    答：用户收到成功、补偿已把 Redis 资格放回，但订单实际仍会落库：Redis 侧可能出现库存多还 1、名单缺人；靠消费端 user+voucher 校验和对账收敛，表现为数量对账告警。

## 二、技术选型题

1. **为什么资格判断放 Redis？**
   答：秒杀热点行在 MySQL 会串行竞争、事务堆积；Redis 内存操作 + Lua 原子判定扛住高并发；MySQL 只做条件扣减兜底。

2. **Lua vs MULTI/EXEC vs WATCH？**
   答：MULTI 不能按读取结果做条件分支；WATCH 乐观冲突要重试、成本高；Lua 服务端一次执行，可判断、可分支、可写多条。

3. **Lua vs Redisson 锁？**
   答：锁会把热点券请求全串行化，还要续期/释放；Lua 无锁、无续期，吞吐高一个量级。锁只用在消费端需要跨 DB 操作的场景。

4. **RocketMQ vs Kafka/RabbitMQ？**
   答：RocketMQ 原生延迟消息、事务消息、重试与死信机制完善，契合"延迟关单 + 重试"；Kafka 无原生延迟，RabbitMQ 延迟依赖插件。

5. **为什么不用事务消息？**
   答：事务消息要求 Broker 回查本地事务状态，而秒杀入口第一笔操作在 Redis，Broker 查不到；用「同步确认 + 失败补偿 + 对账重投」替代。

6. **延迟关单为什么用 RocketMQ，不用扫表/时间轮/ZSet？**
   答：扫表时效差、多实例要防重；时间轮、ZSet 延迟队列要自研轮询/抢占/恢复；MQ 重试死信现成。局限：4.x 固定等级、精度有限。

7. **4.x vs 5.x？**
   答：4.x 只有 18 档固定延迟（level 5 = 1 分钟），不精确；任意时间需升级 5.x 定时消息或自建延迟服务。

8. **XXL-JOB vs Quartz vs @Scheduled？**
   答：@Scheduled 无日志/重试、多实例重复；Quartz 要在业务库维护调度表、偏重；XXL-JOB 调度与执行分离，自带日志、失败重试、路由。

9. **调度中心/执行器分离好处？**
   答：Admin 管定时与日志、可独立高可用；执行器水平扩展、自动注册心跳，业务只写 JobHandler。

10. **为什么选 Caffeine？**
    答：W-TinyLFU 淘汰算法，命中率和内存更优；API 现代；Spring Boot 管理版本，集成成本低。

11. **为什么两级缓存，不只留一层？**
    答：只有 Redis：热点读仍全量走网络；只有 Caffeine：多实例不共享、容量小、重启失效；两级兼顾速度与共享。

12. **逻辑过期 vs 物理 TTL + 互斥锁？**
    答：物理过期瞬间没有旧值，未抢到锁要等待/重试；逻辑过期永远有旧值可返回，只放一个线程重建，响应稳定。

13. **空值缓存 vs 布隆过滤器？**
    答：布隆省内存但有误判、删除和数据同步复杂；空值简单精确、天然支持"后来创建"。小数据量用空值，海量集合用布隆。

14. **为什么滑动窗口？**
    答：防刷要精确限制任意时间窗；固定窗口有临界突刺、令牌桶能攒额度爆发、漏桶不允许突发。

15. **限流方案怎么选？**
    答：网关粗粒度；Sentinel 要部署维护；单机 Guava 多实例不共享；Redis ZSet 集中式、与现有技术栈一致。

16. **为什么用 AOP + 注解，不用拦截器/Filter？**
    答：注解把限流参数声明在方法上，切面按方法精确匹配；拦截器按 URL 适合登录；Filter 拿不到 Spring 方法语义。

17. **Redisson vs 手写 SETNX？**
    答：店铺重建任务短、抢不到直接返回旧值，不需要可重入/续期，SETNX 够用；订单用户锁跨多个 DB 步骤、可能超租期，用 Redisson 看门狗续期。

18. **ID 生成方案对比？**
    答：Redis INCR（本项目）简单、按业务隔离、有网络开销；雪花性能高但要处理机器号与时钟回拨；UUID 无序不适合主键；DB 自增暴露量级、分库麻烦。

19. **为什么拆 tb_seckill_voucher？**
    答：普通券没有库存/时间窗口字段，拆表避免大量 NULL、语义清晰；秒杀信息与券本体一一对应。

20. **为什么不用分布式事务/Seata？**
    答：跨 Redis/MySQL/MQ 强一致事务成本高、可用性差；业务可接受短暂不一致，用幂等 + 消息 + 对账收敛。

21. **为什么用条件更新不加 version？**
    答：状态本身就是版本（只允许 1→2、1→4），条件语义直观、少一列；version 适合字段任意修改的场景。

22. **MyBatis-Plus / Hutool 选型？**
    答：MP 提供 BaseMapper/Lambda Wrapper，减少样板；Hutool 的 JSON/Bean 工具轻量；社区主流、团队熟悉。

23. **换掉 Redis 怎么迁移？**
    答：库存退回 DB 条件扣减 + 分桶/队列串行；缓存退化本地；限流改网关/单机；ID 改雪花；吞吐大幅下降但正确性可保。

24. **只留一种中间件砍哪个？**
    答：砍 MQ（可用 DB 表 + 轮询/对账替代，削峰能力下降）；留 Redis（库存、限流、缓存、ID 都能用）。

## 三、秒杀主链路（面试重灾区）

### 1. 库存一致性（对应文档一）

1. ✳️ **为什么把判断和扣减放进 Lua？拆成几条命令会怎样？**
   答：资格判断由「查库存 → 查重复 → 扣库存 → 记名单 → 写流水」五步组成，单条命令原子不代表组合原子；两个并发请求可能都读到「有库存」再各自扣减，造成超卖/重复。Lua 在 Redis 单线程里一次执行完，中途不会插入其他命令；顺带减少 RTT。

2. ✳️ **Lua 返回 0/1/2/3 分别什么意思？0 以外怎么处理？**
   答：0 成功继续发 MQ；1 库存不足；2 重复下单；3 库存 Key 不存在（未初始化）。1/2/3 都在写操作前返回、不产生脏数据；Java 非 0 直接返回对应失败，不发 MQ。

3. **Lua 返回 null 是什么情况？**
   答：脚本执行异常（Redis 异常等），Java 把 code 兜底为 -1 走默认分支返回失败（fail closed）。

4. 🔁 **Redis 都扣了，为什么 MySQL 还要再扣一次？**
   答：Redis 是「资格库存」负责快速拦截；MySQL 是「持久化库存」是最终事实。条件 `stock > 0` 保证即使 Redis 被误改也不会扣成负数；消费者只有这里成功才创建订单。

5. ✳️ **一人一单怎么保证？现在有什么缺口？**
   答：接入层 Lua `SISMEMBER/SADD`；消费端 `count(user_id, voucher_id)` 联合校验 + 用户锁。缺口：没有唯一索引，最终防线依赖锁与幂等，生产应补 `(user_id, voucher_id)` 唯一索引。

6. **名单为什么用 Set，不用 String / BitMap？**
   答：去重判定 `SISMEMBER` O(1)，语义就是「已抢名单」；String 要自己解析分隔符；BitMap 要求 userId 是连续小整数且无法存任意 ID。

7. **为什么不用 Redisson 锁扣库存？**
   答：热点券所有请求争一把锁会串行化、吞吐崩；且锁续期/释放都有成本。Lua 无锁并行判定。

8. **Redis Cluster 下这段 Lua 有什么问题？**
   答：脚本里自拼多个 Key，Cluster 要求一次脚本访问的 Key 在同一 slot；要改成通过 KEYS 传并给 Key 加 Hash Tag（如 `{voucherId}`）。当前是单机写法。

9. **Lua 里为什么自己拼 Key，不用 KEYS 传？**
   答：写法直观、教程沿袭；规范做法应把 Key 作为 KEYS 传入，便于 Cluster 校验与静态分析（缺口）。

10. **长 Lua 会阻塞 Redis 吗？**
    答：Redis 单线程，执行脚本期间处理不了其他命令，脚本越短越好；本脚本只有几条命令，可接受。

11. **为什么不用「DECR 后为负再补回」？**
    答：DECR 与「判负补回」是两步，两个请求可能同时看到 -1 各补一次，库存被加多；必须原子判断。

12. **为什么先生成 orderId 再传给 Lua？**
    答：orderId 是消费端幂等键、订单主键、对账重投复用的凭据，必须在预扣时确定并写进 reservation。

13. **Redis 库存和 MySQL 库存谁为准？**
    答：MySQL 是事实来源；Redis 是资格快照。不一致时 MySQL 条件扣减兜底、对账告警/修复；极端情况以 DB 重建 Redis。

14. **活动结束后 Redis 库存怎么清理？**
    答：`seckill:stock` 没有 TTL，活动后要人工/定时清理（缺口：当前没有）。

15. **流水 TTL 为什么是 7 天？过期后怎么办？**
    答：覆盖补偿窗口；7 天后仍没对完就失去凭据（当前也没有最大重投次数告警），是已知缺口。

16. **条件扣减影响 0 行为什么抛异常？**
    答：说明 Redis 预扣与 MySQL 库存对不上（Redis 多扣 / DB 异常），此时不能创建订单；抛异常让事务回滚、MQ 重试，并靠对账/告警查根因。

17. **超卖和少卖哪个严重？**
    答：超卖更严重（承诺无法兑现、资损、口碑）；少卖只是少几单、可补偿。设计宁可少卖：条件扣减失败即回滚。

18. **预扣的库存被扣完、但 MQ 全失败会怎样？**
    答：Redis 库存归零、流水一堆、订单 0；对账持续重投或告警；Redis 侧已无库存、活动实际停摆，需要人工介入（缺口：无告警）。

19. **Redis 重启丢数据怎么办？**
    答：stock key 丢失 → Lua 返回 3 → 秒杀直接失败（fail closed）；流水丢失后对账无从下手；需要从 MySQL 重新预热（缺口：无自动恢复）。

20. **同一用户并发点 5 次，Lua 怎么只放进去 1 次？**
    答：Lua 单线程串行，第 1 次 SADD 成功后，其余 4 次 `SISMEMBER` 命中返回 2。

### 2. MQ 与消息幂等（对应文档二）

1. ✳️ **syncSend / asyncSend / sendOneWay 区别？为什么用同步？**
   答：syncSend 阻塞等 Broker 确认、失败抛异常；asyncSend 回调通知；sendOneWay 不等不管。同步是为了确知消息有没有进 Broker，决定继续返回还是补偿。

2. **syncSend 超时 3 秒怎么定的？**
   答：`syncSend(topic, msg, 3000)`；调大减少假失败但拖长接口阻塞，调小误判多、补偿多；且 RocketMQ 内部默认重试 2 次，「抛异常」不完全等于「Broker 没收到」。

3. ✳️ **发送明确失败怎么补偿？为什么脚本先 SISMEMBER？**
   答：执行 `seckill_compensate.lua`：先 `SISMEMBER` 确认资格还在；在则 `SREM + INCRBY + DEL 流水`（撤销预扣），不在则只 `DEL 流水`——先判断再操作，保证重复执行不会把库存加多。

4. 🔁 **接口返回成功 = 订单已创建吗？**
   答：不是。返回 orderId 只代表 Redis 预扣成功 + 消息被 Broker 确认，订单由消费者异步创建。

5. ✳️ **重复消费怎么保证不重复下单？四层各防什么？**
   答：① `getById(orderId)` 防同一条消息重投；② 用户锁防同一用户并发消息；③ `user+voucher` 校验防不同 orderId 同人同券；④ 事务保证扣库存 + 插订单原子。

6. ⚠️ **四层里哪层是主防线、哪层是兜底？**
   答：ID 幂等是第一道；user+voucher 是语义兜底（防新 ID 情况）；事务防半写；用户锁防并发窗口。最根本的是 ID 幂等 + 唯一约束（缺）。

7. **消费端为什么用 Redisson 锁而不是 Lua？**
   答：这里要串行的是「查重 → 扣 DB 库存 → 插订单」多步 DB 操作，Lua 包不了 DB；Redisson 看门狗能在业务超时自动续期。

8. **tryLock 拿不到锁为什么抛异常，而不是等待？**
   答：说明同用户消息正在处理，直接抛异常让 MQ 稍后重试，避免线程阻塞堆积；重试时前一条大概率已提交，幂等通过。

9. 🔁 **假失败（消息已发出、补偿撤销了资格）会怎样？**
   答：消息仍被消费落库；结果订单存在但 Redis 名单没有该用户、Redis 库存多还 1（可能多出 1 个资格）。消费端 user+voucher 会阻止该用户再下单；数量对账会发现名单人数与有效订单数不一致并告警（自动修复有限）。

10. **消息积压怎么办？**
    答：请求线程只等 Broker 确认、不等落库，接口不受影响；恢复时先排查消费异常/慢 SQL/连接池，再扩消费者实例或提高并发度；消费端幂等能承受重复。

11. **为什么不用 RocketMQ 事务消息？**
    答：事务消息需要 Broker 回查本地事务状态，而秒杀入口的「本地状态」在 Redis，回查覆盖不了；用同步确认 + 补偿 + 对账替代。

12. **onMessage 为什么会被自动调用？**
    答：`@RocketMQMessageListener` 让框架创建消费者并注册回调；类实现 `RocketMQListener<String>` 提供 `onMessage`；框架持接口引用，收到消息多态回调你的方法。

13. **消息会丢吗？丢在哪？**
    答：预扣后进程崩溃（没发）→ 对账兜底；发送失败 → 实时补偿；Broker 未落盘 → 同步确认/重试；消费失败 → MQ 重试；重试耗尽 → 死信（无消费者，缺口）+ 对账重投。

14. **MQ 重试多少次？死信谁处理？**
    答：并发消费默认最多重试 16 次后进死信；项目没有死信消费者——但 reservation 还在，对账会继续重投（另一路兜底）。

15. **落库成功但延迟关单消息发送失败会怎样？**
    答：`onMessage` 抛异常 → MQ 重试整条消息 → `createVoucherOrder` 幂等通过后再发延迟消息；若最终死信，订单将一直待支付，且数量对账发现不了（名单与未取消订单数仍一致），是缺口。

16. **getById 幂等和 user+voucher 能互相替代吗？**
    答：不能。ID 幂等只能防同 orderId；出现「新 orderId 同一人同一券」时只有 user+voucher 能拦。

17. **有唯一索引后，用户锁还需要吗？**
    答：理论上可去掉/弱化（并发插入由索引兜底、捕获冲突即重复）；保留锁能减少冲突重试与异常日志；当前没有索引，锁更关键。

18. **CONCURRENTLY vs ORDERLY？**
    答：本项目不要求顺序，并发消费吞吐高；顺序消费要锁定队列串行、吞吐低。

19. **CLUSTERING vs BROADCASTING？**
    答：集群模式一条消息同组内只被一个实例消费；广播模式每个实例都收到。订单必须只落一次，用集群模式。

20. **消息体为什么用 JSON？**
    答：可读、跨语言、易排错；对象序列化有安全与版本兼容问题；JSON 体积略大但可接受。

21. **消费者是一条消息一个线程吗？**
    答：不是，消费者内部是线程池并发拉取/消费，并发度由 `consumeThreadMax` 等配置决定；同一条消息只投给一个消费线程。

### 3. 状态并发控制（对应文档四）

1. ✳️ **支付回调和超时关单同时到达会怎样？**
   答：两边都是 `UPDATE ... WHERE status=1`；数据库行锁保证只有一个把 1 改走，另一个影响 0 行直接结束。避免「先查后改」的覆盖写。

2. **这算乐观锁吗？和 version 字段什么区别？**
   答：是 CAS/乐观并发思想：把旧状态写进条件、靠影响行数判断是否抢到；但没有 version 列，准确叫「状态条件更新」。

3. 🔁 **关单后为什么要回补库存？回补重复执行会怎样？**
   答：未支付订单占库存，关单必须归还（Redis +1、MySQL +1），否则库存泄漏。MySQL 只有状态 1→4 成功那一次才回补；Redis release 脚本先 `SISMEMBER`，重复调用不会重复加。

4. **延迟消息怎么做到「1 分钟后执行」？精确吗？**
   答：消息带 delayTimeLevel，Broker 先存 SCHEDULE_TOPIC，定时扫描到点投真实 topic；是「至少延迟」，误差由扫描粒度决定，不精确。

5. ⚠️ **支付成功但订单已被关闭怎么办？**
   答：当前 `payCallback` 条件更新 0 行、支付被拒（钱进不了系统流程）；生产必须接退款/补偿流程（缺口）。

6. **延迟等级为什么是 5？**
   答：RocketMQ 4.x 固定 18 档，level 5 = 1 分钟；要任意时间升级 5.x 定时消息或做延迟服务。

7. **关单时 Redis 释放失败会怎样？**
   答：`released == null` 抛异常 → MySQL 事务回滚（订单退回待支付）→ MQ 重试；或由对账分支二继续释放。

8. **status 里 3/5/6 是什么？为什么没实现？**
   答：已核销/退款中/已退款；预留状态，属于券后生命周期（缺口）。

9. **`/close/{orderId}` 暴露有风险吗？**
   答：有。接口登录后可调用且没有订单归属校验，任何人拿到 orderId 就能提前关单（缺口）；生产应做内部接口/鉴权/签名。

10. **支付回调怎么鉴权？校验订单归属吗？**
    答：当前只有登录校验，没有验签、没有归属校验（缺口）；真实支付回调必须验签 + 幂等 + 金额核对。

11. **关单先赢、用户又支付了，钱怎么办？**
    答：回调会因状态已是 4 被拒，用户钱可能已在支付渠道被扣，需要退款流程（未实现，缺口）。

12. **和分布式锁做状态流转相比，条件更新好在哪？**
    答：条件更新天然原子、无锁无续期、数据库行锁串行；分布式锁要抢锁/续期/释放，多一层故障点。

13. **为什么不用扫表/时间轮/Redis ZSet 做延迟关单？**
    答：扫表时效差、多实例防重；时间轮/ZSet 要自研轮询、抢占、恢复；MQ 延迟消息重试死信现成。

14. **关单事务里三步的顺序为什么这样？**
    答：先 `getById` 拿券/用户 → 条件更新订单 >> 再回补 MySQL 库存 → 最后释放 Redis；任一步失败整体回滚，Redis 放最后且失败会连 MySQL 一起回滚，靠重试恢复。

15. **延迟消息重复投递会怎样？**
    答：条件更新 0 行 + release 幂等，重投无副作用。

16. **超时时间 1 分钟怎么定？**
    答：演示值；生产按业务定（如 15 分钟），同时受 4.x 延迟等级限制。

17. **关单成功后需要通知用户吗？**
    答：真实业务应发通知（短信/站内信/推送）；当前没有（缺口）。

### 4. XXL-JOB 对账（对应文档五）

1. ✳️ **为什么需要对账？只靠 MQ 重试不够吗？**
   答：预扣后进程崩溃（消息没发）、MQ 积压、假失败、人工误操作——这些实时链路覆盖不了，只能扫描 reservation 发现。

2. ✳️ **重投为什么必须用原 orderId？**
   答：消费端幂等靠 orderId；重投若生成新 ID，一次预扣会被修成多笔订单；复用原 ID 无论投多少次都指向同一订单。

3. 🔁 **对账发现订单已落库，为什么还要 SADD 名单？**
   答：这是成功路径的「销账」：确认用户「已抢到」的资格（正常是空操作，异常时补回），防 Redis 名单丢失后同一用户重复占资格；同时删流水。

4. 🔁 **删流水和撤销预扣的区别？**
   答：流水是「结果未定」的待办条，结果确定就删；撤销 = 还库存 + 移名单，只发生在失败/取消路径。成功路径删流水但不撤销。

5. **XXL-JOB 调度中心和执行器怎么配合？**
   答：执行器启动注册（appName + address，30s 心跳）→ Admin 配任务（JobHandler/Cron/路由/重试）→ 到点 Admin POST /run → 执行器反射调用 reconcile → callback 回报结果 → 失败按配置重试。

6. **reconcile() 为什么不能吞异常？**
   答：Admin 依据执行结果记成功/失败并决定重试；异常被吞会被当成功，补偿永远不重试，流水烂在 Redis 里。

7. **为什么用 SCAN 不用 KEYS？**
   答：KEYS 会阻塞 Redis；SCAN 游标增量遍历，可能重复/不保证一致，但对账场景足够且安全。

8. ⚠️ **补偿能无限重试吗？**
   答：当前记录 retryCount/lastRetryAt 但没有最大次数、告警和人工入口，允许每 60s 一直重投——已知缺口。

9. **Admin 挂了会怎样？**
   答：调度停摆、注册信息过期；业务链路不受影响；恢复后按 Cron 继续，期间不一致靠补跑收敛。

10. **xxl_job 那么多表，会像 Quartz 抢锁吗？**
    答：只有一行 `schedule_lock`，`FOR UPDATE` 只在 5 秒一轮的扫描事务里持毫秒级；触发和回调不持锁。Quartz 是每次触发抢 `QRTZ_LOCKS` + 触发器表锁，量级不同。

11. **JobHandler 名字和 @XxlJob 对不上会怎样？**
    答：执行器本地 Map 找不到 → `jobHandler not found`，任务失败；名字是跨进程唯一约定。

12. **路由策略和阻塞策略？**
    答：路由决定多台执行器选谁（故障转移可换机）；阻塞策略（串行）防上一轮没跑完下一轮又触发。

13. **对账频率怎么定？**
    答：1 分钟是时效与开销的折中；太稀不一致窗口长，太频空转；数据量大要分片。

14. **对账扫全量会不会慢？**
    答：SCAN count=100 渐进遍历；后续可按时间/券分片、只扫最近窗口。

15. **数量对账为什么不自动修？**
    答：Redis 人数 vs 未取消订单数不一致时无法安全推断该加还是该减（可能名单丢、可能订单丢）；自动改可能引入更大错误，先告警人工介入。

16. **30 秒等待窗口、60 秒重投间隔怎么定？**
    答：30s 给正常消费留落库时间，避免过早重投；60s 防同一笔预扣每轮都重发造成风暴。

17. **重投消息和正常消息有区别吗？**
    答：没有，同一 topic、同一消费者，靠消费端幂等消化；重投只是复用原 orderId。

18. **执行器多台，对账会重复跑吗？**
    答：单次调度按路由只发一台；失败重试/故障转移可能换机器再跑，所以补偿动作必须幂等（重投用原 ID、释放用 Lua 判断）。

19. **retryCount 更新顺序能不能反？**
    答：先 syncSend 成功后 increment/put；若发送成功但计数更新失败，最坏下轮再投一次（幂等无害）；若先记账后发送失败可能漏投，更糟。

20. **执行器注册 IP 127.0.0.1 有什么问题？**
    答：单机 localhost 可用；多机/容器中 Admin 需要能访问执行器真实 IP，否则调度发不过去。

21. **accessToken 干嘛的？**
    答：执行器与 Admin 通信的鉴权令牌，两边一致才允许注册/回调。

### 5. 缓存治理（对应文档三、七）

1. ✳️ **击穿 / 穿透 / 雪崩分别是什么？怎么防？**
   答：击穿 = 单个热点 Key 失效瞬间并发回源（逻辑过期 + 互斥重建防）；穿透 = 数据缓存和 DB 都不存在（空值缓存防）；雪崩 = 大量 Key 同时失效或 Redis 整体不可用（本项目未专门做，靠 TTL 打散/多级缓存）。

2. ✳️ **逻辑过期和物理过期区别？为什么必须预热？**
   答：逻辑过期 Key 不过期，Value 里带 `expireTime`；过期后先返回旧值、单线程重建。Key 不存在时方案不会自动回源，所以必须提前写入（预热）。

3. **逻辑过期重建时其他请求为什么不阻塞？**
   答：抢不到锁不等待，直接返回旧值。

4. **重建失败会怎样？**
   答：线程池任务抛异常、锁在 finally 释放；旧值继续服务直到下次重建成功（可能长期旧值），需要监控日志（缺口）。

5. **expireTime 谁维护？**
   答：`setWithLogicalExpire` 写入 `now + TTL`，重建时刷新。

6. **两级缓存为什么加 Caffeine？多实例不一致怎么办？**
   答：本地缓存抗热点、降 Redis 压力；不一致靠 5 秒 TTL 收敛，未做广播失效（缺口）。

7. 🔁 **库存为什么不做缓存？**
   答：高频变化且直接影响秒杀；详情页每次 `fillLiveStock` 实时读 `seckill:stock:{id}`。

8. **缓存和数据库怎么保持一致？**
   答：标准 Cache Aside：先更新数据库、再删缓存；删除失败靠 TTL 收敛。⚠️ 本项目 `addSeckillVoucher` 的删除发生在事务提交前，有并发回填旧数据的窗口（严谨做法：提交后删/延迟双删）。

9. **空值缓存 TTL 为什么只有 2 秒？**
   答：短 TTL 兼顾防穿透与「数据后来创建」的及时性。

10. **空值缓存和布隆过滤器怎么选？**
    答：布隆省内存但有误判、删除复杂；空值简单精确。海量固定集合用布隆，小规模用空值（本项目组件已封装）。

11. **Caffeine 的 key/value？getIfPresent 和 get 区别？**
    答：`localVoucherCache`: shopId→List\<Voucher\>；`localSeckillDetailCache`: voucherId→DTO。`getIfPresent` 只查不加载、未命中返回 null；`get(key, loader)` 未命中调 loader 并回填。

12. **为什么 expireAfterWrite 而不是 expireAfterAccess？**
    答：write 写后固定过期、读不续期，能把多实例不一致窗口锁在 5 秒；access 高频读会不断续期、窗口不可控。

13. **maximumSize 1000 怎么定的？**
    答：估算的店铺/券量级；超过按 W-TinyLFU 淘汰。

14. **新增普通券为什么没走缓存失效？**
    答：`addVoucher` 只 `save`，没删缓存，新券最多 30 秒后可见（缺口，靠 TTL 兜底）。

15. **Redis 被清空后 Caffeine 能顶住吗？**
    答：5 秒内本机缓存还能服务；之后回源 MySQL 重建 Redis，涌入流量可能打一阵 DB，需限流/熔断配合。

16. **回填顺序为什么先 Redis 后 Caffeine？**
    答：先写共享层（Redis）再写本机层，避免其他实例读不到新值而本机已「新」，扩大不一致。

17. **秒杀券详情页库存怎么保证实时？**
    答：每次返回前 `fillLiveStock` 读 Redis；读不到保留 MySQL 快照（降级）。

18. **为什么先更库再删缓存，不直接更新缓存？**
    答：删缓存让下次读统一回源重建，避免并发双写覆盖（两个更新乱序写出旧值）；直接更新缓存结构复杂、并发风险高。

19. **逻辑过期和两级缓存分别适合什么数据？**
    答：逻辑过期适合热点、可容忍旧值、要防击穿；两级缓存适合读多写少、多实例热点、字段可分级。库存等强一致数据都不适合。

20. **生产上缓存预热怎么做？**
    答：启动任务/定时任务/运营操作写入（本项目建券时写库存即写时预热；逻辑过期依赖提前写入）。

### 6. 限流（对应文档六）

1. ✳️ **滑动窗口为什么用 ZSet？member/score 是什么？**
   答：要「任意 1 秒内最多 N 次」：score=请求时间戳，`ZREMRANGEBYSCORE` 删窗口外、`ZCARD` 精确计数；member=时间戳-随机数保证唯一（防同毫秒覆盖）。

2. ✳️ **为什么不用令牌桶 / 漏桶 / 固定窗口？**
   答：固定窗口临界翻倍；漏桶不允许突发；令牌桶能攒额度一次性爆发；防刷要任意窗口精确。

3. 🔁 **限流和防超卖的关系？**
   答：限流保护资源和入口（流量维度），不保证库存正确；Lua 预扣保证业务正确（库存维度）；前后两道，不能替代。

4. **Redis 挂了限流放行还是拒绝？**
   答：当前 Redis 异常或返回 0 都拒绝（Fail Closed），保护秒杀；生产可按接口分级降级。

5. **按 IP 限流有什么坑？**
   答：`X-Forwarded-For` 可伪造、NAT 下多用户共用出口 IP、代理层数影响取值；只应信任受控网关写入的头。

6. **一个 Lua 怎么同时服务秒杀和商铺？**
   答：脚本只依赖 KEYS/ARGV（key、窗口、阈值、时间），参数由注解 → 切面读取后传入；新增接口只加注解。

7. **member 为什么拼随机数？**
   答：member 内容不重要、唯一性重要；不唯一会导致同毫秒请求互相覆盖、zcard 少计数、超限放行。

8. **阈值怎么定？**
   答：业务经验 + 压测调整；演示值秒杀 1s 5 次、商铺 1s 20 次；上线看误伤率。

9. **ZSet 方案内存开销？**
   答：每个请求一个 member，高 QPS 高基数下内存与 O(logN) 成本明显；可换滑动窗口计数/分桶/网关本地限流。

10. **为什么不用 HTTP 429？**
    答：项目统一 `Result{success,errorMsg}` 包装、返回 fail 文案；HTTP 语义上 429 更标准（差异点）。

11. **怎么支持动态调整阈值？**
    答：注解值改读配置中心/Admin；当前硬编码。

12. **业务方法抛异常，切面会怎样？**
    答：`proceed()` 的异常不会被切面吞掉，原样上抛（事务回滚正常），只是不会返回限流文案。

13. **类和方法同时打注解会怎样？**
    答：当前切点是方法注解 `@annotation(...)`，类级不生效；要支持需加类级切点和合并逻辑（缺口）。

14. **限流切面和事务切面的顺序？**
    答：限流注解在 Controller、事务在 Service；Controller 切面先执行（外层），通过后才进入事务。

15. **单机限流 vs 分布式限流？**
    答：单机计数器多实例各自计数、总量会超；需要集中式（Redis）或网关/Sentinel；分布式多一次网络开销但计数准确。

## 四、横切与架构

1. ✳️ **画一下从「用户点击秒杀」到「订单落库」的全链路。**
   答：限流 → Lua 预扣（库存-1、SADD、写 reservation）→ syncSend → 消费者幂等/用户锁/联合校验/条件扣库存/插订单 → 发延迟关单消息；异常由失败补偿 + MQ 重试 + XXL-JOB 对账兜底。

2. ✳️ **这条链路哪里可能不一致？如何收敛？**
   答：四个窗口：预扣↔落库（对账重投）、落库↔关单（延迟消息重试）、取消↔释放（release + 对账分支二）、缓存↔DB（TTL + 先库后删）。统一思路：幂等 + 消息 + 对账。

3. **故障演练（连环）：**
   - Redis 挂：Lua 执行失败 → 秒杀 fail（fail closed）；限流 fail closed；店铺逻辑过期仍有旧值可用但重建失败；库存 key 丢则会返回 3。
   - MQ 挂：syncSend 失败 → 补偿 → 接口失败用户重试；已预扣未发成功的靠对账。
   - XXL-JOB 挂：对账停摆、不一致积累；业务链路不受影响。
   - MySQL 出问题：落库失败 MQ 重试；查询失败接口报错。
   - 发版重启：预扣后、消息前崩溃的请求由对账兜底。

4. **接口返回成功但用户查不到订单，怎么排查？**
   答：看 reservation 是否存在 → 消息发送日志（syncSend）→ 消费日志（幂等/异常）→ 订单表 → 对账任务日志；定位是「失败」还是「还没到」。

5. **只保留三个优化，留哪三个？**
   答：Lua 预扣（正确性）、MQ 异步（吞吐）、对账（兜底）。其余都是锦上添花。

6. **容量大概多少？瓶颈在哪？**
   答：Redis 预扣是内存操作、很轻；瓶颈先后在消费落库（DB 连接/行锁）和 MQ；本地压测只看趋势，不代表生产。

7. **要监控哪些指标？**
   答：QPS/成功率/P99、Redis 库存与名单人数、reservation 数量与重投次数、消息积压、对账差异数。

8. **日志怎么串？**
   答：入口生成 traceId，MDC 透传日志，MQ 消息属性携带，消费端恢复上下文。

9. **数据库连接池多大？**
   答：默认 HikariCP，按压测调 max；消费并发度要和连接池匹配，否则互相等。

10. **Redis 怎么部署的？挂掉丢什么？**
    答：演示是单机；RDB 快照间隔或 AOF everysec 会丢少量数据；丢 stock key 会导致秒杀不可用（返回 3）。

11. **RedisIdWorker 怎么生成 ID？时钟回拨怎么办？**
    答：`(当前秒 - 2022-01-01) << 32 | 当日 INCR 序列`，Key `icr:{prefix}:{yyyyMMdd}`；时钟回拨会让前缀变小、不再严格递增；单日 2^32 序列够用。

12. **接口安全上有哪些风险？**
    答：支付回调无验签/归属校验、/close 任何人可调、无风控防黄牛；重放靠状态条件更新兜一部分（缺口）。

13. **幂等、防重、限流的区别？**
    答：幂等 = 重复执行结果一致（消费端）；防重 = 阻止重复提交（入口 token/锁）；限流 = 控制速率。三个不同层次。

14. **流量翻十倍先改哪里？**
    答：先扩消费能力（消费者/分片），再加库存分桶/热点拆分，最后才 DB 扩容；限流阈值同步收紧。

15. **上线前检查什么？**
    答：中间件连通、库存预热、任务配置、压测、告警、回滚方案、数据初始化、灰度。

## 五、反套路与压力题

- ⚠️ **这些是教程里的吧？你改了什么？**（照〇-2 答：主动区分教程部分与扩展部分）
- **现场看代码**：如 `reconcile()` —— 开关判断 → `repairReservations()`（扫描 + 三分支）→ `reconcileActiveOrderCounts()` → `hasFailure` 抛异常让 Admin 重试。
- **白板题：**
  - 条件扣库存：`UPDATE tb_seckill_voucher SET stock=stock-1 WHERE voucher_id=? AND stock>0`
  - 状态条件更新：`UPDATE tb_voucher_order SET status=2 WHERE id=? AND status=1`
  - 滑窗核心：`ZREMRANGEBYSCORE key 0 now-window*1000` → `ZCARD` → `>=limit` 则 return 0 → `ZADD` → `EXPIRE` → return 1
  - `seckill.lua` 伪代码：GET stock（null→3、<=0→1）；SISMEMBER（命中→2）；INCRBY -1；SADD；HSET reservation；EXPIRE；return 0
  - 支付 vs 关单时序：两个条件 UPDATE 抢同一行，一个 1 行、一个 0 行
- **不允许用 Redis，秒杀怎么改？**
  答：DB 乐观锁/条件扣减 + 队列串行削峰；分桶降低热点行竞争；缓存退化本地；性能与体验大降，只适合小规模。
- **哪里可以更简单 / 被 review 挑什么？**
  答：Lua 自拼 Key（Cluster 不兼容）、返回值小整数可读性差、用户锁+唯一索引功能重叠、对账无重投上限、缓存删除在事务内、魔法数字多。
- **Redis 库存变 -1 怎么排查？**
  答：查是否有绕过 Lua 的写入路径、补偿脚本是否重复执行（已用 SISMEMBER 防）、历史脏数据、人工改库；先止损（暂停活动）再修数据。
- **用户投诉「抢到了没订单」怎么定位？**
  答：reservation 是否存在 → MQ 发送/消费日志 → 订单表 → 对账记录；区分"失败"还是"延迟未到"。
- **一致性、可用性、成本怎么排？**
  答：秒杀优先可用性，但库存正确是底线（fail closed）；一致性用最终一致兜；成本最后。
- **最有把握 / 最没把握？**
  答：把握：预扣 + 幂等；没把握：Admin 端到端验证与真实流量表现。
- **还有哪些点没讲到？**
  答：GEO 附近商铺、签到、关注 Feed、Caffeine 等本项目其他模块。

## 六、开放设计题（白板 / 口述）

1. **设计一个「优惠券核销系统」。**
   答：状态机（已支付→已核销）；幂等（核销记录唯一键或条件更新只成功一次）；权限（店员角色+门店绑定）；并发（行锁/条件更新）；离线兼容（先本地后同步）；可追溯（操作人/时间/门店）。
2. **设计「退款流程」。**
   答：状态机 2→5 退款中→6 已退款；调用支付渠道退款 + 回调确认；幂等（退款单号）；金额校验；券作废或库存回补按业务定；与关单/核销并发用条件更新裁决。
3. **设计一个「对账系统」。**
   答：口径（订单/流水/金额）；定时 + 增量；差异分类（时序差异/真差异/系统差异）；自动修规则与白名单；人工工单；差异台账 + 报表 + 告警。
4. **重新设计「订单超时关单」。**
   答：扫表（简单、时效差）、时间轮（内存、重启恢复难）、Redis ZSet 延迟队列（有序、自研轮询）、MQ 延迟（现成、精度差）、RabbitMQ 死信（需插件/队列 TTL）；按精度与运维成本选。
5. **设计「秒杀容量评估」。**
   答：Lua 预扣 O(1) 内存操作，单机 Redis 可达数万~十万 QPS；瓶颈在消费落库与 DB 行锁；估算方法：并发数 × 平均 RT = QPS 容量，再用压测校准。
6. **设计「消息不丢」。**
   答：生产端同步确认 + 重试 + 本地补偿；Broker 同步刷盘/主从；消费端手动 ACK + 重试 + 死信 + 幂等；全链路对账兜底。
7. **设计「防刷 / 风控」。**
   答：设备指纹、行为序列、多维度频控、风险触发验证码、黑名单/白名单同步；与限流配合（限流保底、风控精打）。
8. **设计「库存分桶」。**
   答：100 库存拆 10 个桶，请求哈希到桶、桶内 Lua 扣减；桶空时可借调或路由；汇总对账（各桶余量之和 = 总库存）。
9. **设计「跨实例缓存失效」。**
   答：Redis Pub/Sub（轻、可能丢）、MQ 广播（可靠、重）、CDC（DB 变更驱动、链路长）、版本号 + 短 TTL 兜底；按一致性要求选。
10. **设计「秒杀降级预案」。**
    答：Redis 挂 → 秒杀停（fail closed）；MQ 挂 → 入口限流或同步落库降级；DB 压力大 → 收紧限流、延长缓存、关非核心接口。
11. **把秒杀改成「预约 + 抽签」。**
    答：预约阶段幂等去重（一人一号）→ 定时抽取（随机/权重）→ 中签发资格 → 支付；无瞬时抢购压力，但流程更长、体验不同。
12. **怎么发现热点 Key？**
    答：本地滑动窗口统计 + 上报聚合；或 Redis 监控/代理采样；发现后自动加入本地缓存、限流、告警。

## 七、业务指标题

1. **核心业务指标有哪些？**
   答：下单成功率、接口 P99、超卖率（目标 0）、对账差异数、消息积压量、重投成功率。
2. **什么是资损？可能有哪些？**
   答：超卖（多卖券）、少卖（少收入）、重复发券、金额配置错误、退款失败导致的资金占用。
3. **超卖 vs 少卖哪个严重？**
   答：超卖更严重：承诺无法兑现 + 资损 + 口碑；宁可少卖（失败回滚）。
4. **对账时效 SLA 定多少？**
   答：分钟级（当前 1 分钟一轮）；业务要求更快则缩短周期 + 分片扫描。
5. **QPS 怎么拆？**
   答：入口 QPS（含被限流/重复）→ 通过限流 QPS → 预扣成功 QPS → 消息 QPS → 落库 TPS。
6. **怎么衡量缓存优化有效？**
   答：Redis GET 次数下降、P99 降低、L1/L2 命中率、DB 读 QPS 下降。
7. **限流拦了多少、误伤多少？**
   答：拦截数/拦截率来自切面日志；误伤率看被拦用户的正常行为比例；据此调阈值。
8. **可用性目标？**
   答：99.9%+；秒杀期间允许降级（关闭非核心接口、延长缓存）。
9. **落库延迟目标？怎么监控？**
   答：秒级；用消息发送时间戳 + 订单创建时间统计分布（P50/P99），或对账流水扫描间隔估算。
10. **最终一致窗口业务能接受多长？**
    答：缓存 5~30 秒、对账分钟级；券信息可接受，库存不可（实时）。
11. **对账差异率多少算正常？**
    答：正常应趋近 0（瞬时差除外）；持续差异或数量超阈值要告警。
12. **一人一单防刷效果怎么衡量？**
    答：重复下单拦截数、相关投诉率、异常账号数（结合风控）。
13. **业务指标怎么反过来影响技术方案？**
    答：支付成功率低查回调；取消率高查关单时长；秒杀成功率低查库存与限流配置。
14. **大促后「少卖了」怎么复盘？**
    答：对比 Redis 预扣数、消息数、订单数、库存变化，定位在限流/预扣/发送/消费/DB 哪一段。
15. **补偿成功率怎么监控？**
    答：重投成功数 / 重投总数、平均重投次数、最终人工介入数。

## 八、团队协作与沟通题

1. **这个方案怎么给团队讲清楚？**
   答：背景（为什么做）→ 目标/指标 → 方案与图 → 关键取舍 → 风险与兜底 → 验证与回滚。

3. **怎么评估一个优化值不值得做？**
   答：收益（指标改善）/成本（人天、运维）/风险（不一致、故障面）/可回滚性；小步验证。
4. **产品要求「绝不超卖」，怎么对齐？**
   答：技术能保证「不超卖」（条件扣减 + 对账可证），但不能保证 100% 秒杀成功；对齐口径是超卖 vs 失败率。
5. **上线怎么和测试、运维对齐？**
   答：功能/并发/异常注入测试；中间件、告警、容量对齐；业务文案与客服口径；灰度与回滚方案。
6. **线上对账差异怎么组织排查？**
   答：先止损（暂停活动/入口）、再定位（对账报表/日志/流水）、后修复（脚本/人工）、复盘补监控。
7. **文档怎么写让新人能接手？**
   答：总览图 + 状态机 + Key/表结构 + 失败矩阵 + 运维手册（任务、告警、清理）。
8. **怎么说服 leader 不用 Seata？**
   答：讲成本/可用性/业务容忍度，给替代方案（幂等 + 对账）和影响评估，用数据说话。
9. **跨团队联调怎么推进？**
   答：接口契约先行、Mock 联调、时间表、责任人与问题清单。
10. **两周排期怎么拆？**
    答：先正确性（预扣 + 幂等）→ 再吞吐（MQ）→ 再兜底（对账）→ 最后优化（限流/缓存），每步可独立验证。
11. **review 最关注什么？**
    答：正确性（并发/边界）、幂等、异常处理、资源占用、可观测性、命名与重复。
12. **怎么带新人做这个模块？**
    答：先讲业务与链路，再讲模块边界与代码入口，给一个小任务（如加监控），结对 review。

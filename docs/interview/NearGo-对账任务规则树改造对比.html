一、这次改造的逻辑在干什么

SeckillReconciliationTask 是 XXL-JOB 定时任务（@XxlJob("seckillReconcileJob")），负责秒杀链路的最终一致性兜底。它有 4 件事，其中第 1 件就是本次改造的对象：

  1. 修复预扣（本次改造）：扫描 seckill:reservation:* 预扣记录，逐条判断并处置：未落库 → 重投 MQ已取消 → 释放预扣已落库 → 补一人一单标记未到窗口 → 跳过
  2. 数量对账：Redis 名单人数 vs DB 有效订单数，不一致打警告（未改）
  3. XXL-JOB 失败语义：单条失败累计 hasFailure，最后抛异常让调度标记失败（未改）
  4. 开关节流：seckill.reconcile.enabled=false 直接跳过（未改）
关键点：每条预扣记录要按「订单状态 + 时间窗口」做一次多分支决策。这就是天然的决策树 —— 改造要做的只是把这棵树从过程代码里「拎出来摆明」。

2.1 原版骨架代码（编号为流程分支点）

// SeckillReconciliationTask.java（改造前，75 行的 repairReservations()）
while (cursor.hasNext()) {
  try {
    fields = opsForHash().entries(key);
    orderId/userId/voucherId/reservedAt = parseLong(...) 全解析;

    if (任一解析失败) { hasFailure = true; continue; }              // ① 元数据不全

    order = voucherOrderMapper.selectById(orderId);

    if (order == null) {                                              // ② 未落库
      if (!shouldRetry(fields, reservedAt)) continue;                 // ③ 未到窗口，静默跳过
      try { syncSend(...); increment(retryCount); put(lastRetryAt); }   // ④ 重投
      catch (Exception e) { hasFailure = true; ... }                  //    重投失败
      continue;                                                       // ⑤ ★关键：使 ⑥ 与 ② 平级
    }

    if (Integer.valueOf(4).equals(order.getStatus())) {               // ⑥ 已取消
      released = releaseRedisReservation(...);
      if (released == null) { hasFailure = true; ... }                 // ⑦ 释放失败
      else log.info(...);
    } else {                                                            // ⑧ 已落库
      opsForSet().add(orderKey, userId); delete(key);
    }

  } catch (Exception e) { hasFailure = true; ... }                      // ⑨ 单条兜底
}

四、装配与数据流

五条铁律（照搬模板时必须守住）：① 节点单例，一次请求的数据绝不放成员变量，全部走 Context；② 节点里只 throw 不 catch，业务异常统一冒泡到任务循环；③ 装配只做一次（启动期 @Resource / @Bean 注入）；④ 一次请求一个 Context，在循环里 new；⑤ 引擎 100 步上限防环，装配错误会直接炸出来而不是死循环。

七、收益与代价（诚实版）

收益（按含金量排序）

  1. 扩展成本：新增「重投超 N 次转人工告警」「支付超时但未关单」这类补偿，只需加节点 + 改一行 next()，主干与既有分支零回归
  2. 分支显式化：对账是长期在后台跑的兜底逻辑，最怕「顺手改了 else」埋雷；现在改分支先看 next()，新状态不会被静默吞掉
  3. 可观测性：RepairOutcome 让 XXL-JOB 从「成功/失败」升级为「重投 X 条、释放 Y 条、修复 Z 条、跳过 W 条」
  4. 复用资产：framework/rule 与业务解耦，将来其它多分支流水线可整包搬走
  5. 面试叙事：有完整的「为什么用树不用链、为什么不继续 if-else、代价是什么」故事

代价（同样要说清楚）

  1. 类数量 +12，读代码要先看装配关系（next 指向）
  2. 调用栈变深：FlowEngine.run → node.process → handle，单步调试略绕
  3. 分支只有 2~3 个的简单场景不该上规则树，本任务有 7 个出口才值得
  4. 节点单例约束强：写代码时忘记把数据放 Context 就会出并发 Bug
  5. 收益兑现依赖「分支还会继续长」；若补偿逻辑就此冻结，改造票价收不回
结论：这是全项目最值得用规则树的一处（数据状态驱动的多出口决策）。但它不是「必须改」——买的是未来的扩展性、可观测性和一段能讲清楚的设计决策。

八、面试问答（改造后能讲什么）

Q1：为什么用规则树不是责任链？
处置动作由订单状态「分叉」——未落库去重投、已取消去释放、已落库去补标记，是树形；责任链适合「顺序全过、一关不过就断」的校验场景，这里没有固定顺序关卡，用链反而表达不了分支。
Q2：怎么保证改造行为不变？
先列出真值表（输入状态 → 原路径 → 新节点），逐条对齐；Redis Key 拼接、回滚脚本、MQ 参数、重试窗口、失败计数口径全部保留；失败统计仍是「单条 catch 累计 hasFailure，最后抛异常给 XXL-JOB」。
Q3：引擎会不会死循环或装配错误？
FlowEngine 有 MAX_STEPS=100 防环保护，成环直接抛 IllegalStateException；单测覆盖顺序执行、分支跳转、终点收口、防环四种情况。
Q4：节点是单例，线程安全吗？
安全。节点无状态，所有一次请求的数据放在每次循环 new 出来的 ReservationContext 里，类里不存任何请求级成员变量（五条铁律之一）。
Q5：更简单的重构行不行？
行。把重投/释放/修复抽成三个方法也能消掉嵌套，但「分支决策」仍藏在方法内的 if 里；规则树多买的是「分支声明独立成层 + 统一出口」。选不选取决于分支会不会继续增长——这也是改造前要先想清楚的问题。

九、附录：引擎完整源码（约 60 行，可整包搬走）

// FlowNode.java —— 节点接口
public interface FlowNode<T, C, R> {
    R process(T request, C context) throws Exception;          // 本节点业务
    FlowNode<T, C, R> next(T request, C context) throws Exception; // 下一跳（null = 终点，分支写这）
}

// AbstractFlowNode.java —— 抽象节点：定死"先补数据、再干活"
public abstract class AbstractFlowNode<T, C, R> implements FlowNode<T, C, R> {
    @Override
    public R process(T request, C context) throws Exception {
        loadData(request, context);      // 钩子：默认空
        return handle(request, context); // 子类必填
    }
    protected void loadData(T request, C context) throws Exception { }
    protected abstract R handle(T request, C context) throws Exception;
}

// FlowEngine.java —— while 驱动全树 + 防环
public final class FlowEngine {
    private static final int MAX_STEPS = 100;
    private FlowEngine() { }

    public static <T, C, R> R run(FlowNode<T, C, R> start, T request, C context) throws Exception {
        FlowNode<T, C, R> node = start;
        R result = null;
        int step = 0;
        while (node != null) {
            if (++step > MAX_STEPS) {
                throw new IllegalStateException("规则树疑似成环（超过 " + MAX_STEPS + " 步）");
            }
            result = node.process(request, context);
            node = node.next(request, context);
        }
        return result;
    }
}

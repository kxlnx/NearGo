## 大问题一：请完整讲一下你的秒杀库存一致性方案，Redis + Lua、MySQL 条件扣库存和一人一单是如何配合的？

### 对应简历亮点

> 基于 Redis + Lua 原子完成优惠券库存校验、库存预扣和用户去重，再结合 MySQL 条件扣库存，避免并发场景下库存扣减为负数和同一用户重复下单。

### 面试官考察点

- 是否真正理解超卖产生的原因；
- Lua 的原子边界是什么；
- 为什么 Redis 扣过库存，MySQL 还要再扣一次；
- 一人一单是否只有一层判断；
- Redis 与 MySQL 不一致时如何收敛；
- 是否把业务幂等错误地说成数据库强约束。

### 30 秒结论

秒杀请求不会直接进入 MySQL，而是先通过 Redis Lua 原子完成库存检查、用户去重、库存预扣和预扣元数据写入。预扣成功后才发送 RocketMQ，消费者落库时再使用 `stock > 0` 条件扣减 MySQL 库存，并通过订单 ID、用户与优惠券联合校验以及用户粒度锁处理重复消费。Redis 负责高并发入口和快速失败，MySQL 负责最终持久化事实，两者之间出现的短暂不一致由发送失败补偿和 XXL-JOB 对账任务处理。

### 2～3 分钟完整口播

这个问题最开始的风险是，如果每个秒杀请求都在数据库中先查库存再扣减，那么“查询库存”和“修改库存”之间不是一个原子操作，并发时多个请求可能同时读到库存充足；同时大量最终失败的请求也会占用数据库连接和事务资源。因此我把第一层资格判断前移到 Redis。

请求进入后先生成订单 ID，然后执行 Lua 脚本。脚本依次检查库存 Key 是否存在、库存是否大于零、用户是否已经在当前优惠券的下单集合中；满足条件后扣减 Redis 库存、将用户加入集合，并写入包含订单 ID、用户 ID、优惠券 ID和预扣时间的元数据。因为这些命令在同一个 Lua 脚本中执行，所以不会出现库存已经扣了但用户标记还没写入的线程交叉问题。

Redis 预扣并不代表订单已经完成，预扣成功后还要把订单消息发送到 RocketMQ。消费者落库时会先按订单 ID 判断消息是否重复，再按用户和优惠券判断是否已经存在业务订单，并使用用户粒度的 Redisson 锁防止同一用户消息并发穿过检查。真正修改 MySQL 库存时使用 `stock > 0` 的条件更新，受影响行数为一才创建订单，所以即使 Redis 库存被误改，数据库也不会扣成负数。

这个方案不是 Redis 和 MySQL 的强一致事务，而是入口原子预扣、数据库条件更新、消息幂等和定时对账共同实现的最终一致性。当前数据库还没有 `(user_id, voucher_id)` 唯一索引，所以面试时我会明确说明，一人一单目前主要依赖 Lua、业务校验和用户锁，生产化还应增加数据库唯一约束作为最后一道防线。

### 实际执行流程

```text
请求进入
  → 生成订单 ID
  → Lua 检查 Redis 库存
  → Lua 检查用户是否重复购买
  → Lua 扣减库存、记录用户、写入预扣元数据
  → 同步发送 RocketMQ
  → 消费端检查订单 ID
  → 用户粒度 Redisson 锁
  → 检查用户 + 优惠券是否已有订单
  → MySQL 执行 stock > 0 条件扣减
  → 创建订单
```

### 为什么这样选

| 方案 | 没有作为入口主方案的原因 |
|---|---|
| Java `synchronized` | 只能保护单个 JVM，多实例部署后失效 |
| 数据库悲观锁 | 热点库存行会串行化，事务连接和锁等待压力大 |
| 数据库乐观锁 | 能防超卖，但大量失败更新仍然直接冲击数据库 |
| Redisson 全局库存锁 | 所有请求竞争同一把热点锁，吞吐受锁串行限制 |
| Redis Lua | 可以把判断、扣减、去重和记录作为一个原子操作，因此用于入口预扣 |

### 高频追问

#### 追问 1：Lua 能保证 Redis 和 MySQL 一起原子吗？

不能。Lua 只能保证 Redis 内部脚本执行期间的原子性，无法把 Redis 与 MySQL 纳入同一个本地事务。项目通过 RocketMQ 异步落库、消费端幂等、发送失败补偿和 XXL-JOB 定时对账实现最终一致性。

#### 追问 2：为什么 Redis 扣完库存，MySQL 还要扣？

Redis 库存是秒杀入口的资格库存，用来挡住大部分失败请求；MySQL 库存是持久化事实。消费者仍执行 `stock > 0` 条件更新，可以防止 Redis 数据异常或补偿错误导致数据库库存扣成负数。

#### 追问 3：为什么不用你之前提到的“库存座位号”方案？

座位号或 fencing token 更适合需要抵御人工回补、重复回滚和库存计数被异常修改的场景。当前项目卖的是优惠券资格，现有 Lua 预扣、用户集合、数据库条件扣减和补偿链路已经覆盖主要并发问题。若后续存在频繁人工改库存或复杂回补，可以增加库存批次或唯一库存凭证，但这不是当前源码已经实现的能力。

#### 追问 4：Redis Cluster 下这段 Lua 有什么问题？

当前脚本直接拼接多个 Key，适合单节点 Redis。Redis Cluster 中同一脚本访问的多 Key 必须落在同一 Slot，生产化需要将 Key 通过 `KEYS` 传入，并使用 Hash Tag 保证同槽。

#### 追问 5：一人一单为什么还要加数据库唯一索引？

业务查询和分布式锁可能因为代码缺陷、锁配置或异常路径失效，数据库唯一索引是持久化层不可绕过的最后约束。当前仓库尚未添加该索引，所以不能把它写成已经实现。

## 大问题二：为什么引入 RocketMQ，它如何完成异步削峰、消息幂等和异常恢复？为什么没有选择 Kafka？

### 对应简历亮点

> 引入 RocketMQ 将秒杀请求与订单落库流程解耦，通过订单 ID 幂等、用户与优惠券联合校验以及数据库事务保证重复消费不重复创建订单。

### 面试官考察点

- 是否理解削峰，而不只是“用了 MQ”；
- 接口返回成功的业务语义；
- 发送失败、重复消费、消费异常和消息积压如何处理；
- RocketMQ、Kafka、RabbitMQ、Redis Stream 的选型差异；
- 是否错误宣称 Exactly Once 或事务消息。

### 30 秒结论

引入 RocketMQ 后，HTTP 请求只负责 Redis 资格判断和可靠入队，数据库写入由消费者按照自身处理能力异步完成，避免秒杀峰值直接冲击 MySQL。生产端使用同步发送确认 Broker 是否接收，明确失败时回滚 Redis 预扣；消费端假设消息可能重复，通过订单 ID、用户券业务键、用户锁和数据库条件更新实现幂等。选择 RocketMQ 是因为当前链路既需要订单业务消息，也需要延迟消息完成超时关单，相比 Kafka 更符合当前业务模型。

### 2～3 分钟完整口播

原来的同步下单方式会把 Redis 校验、数据库库存扣减和订单插入全部放在一次 HTTP 请求中。秒杀流量突然升高时，请求峰值会直接传递到 MySQL。引入 RocketMQ 后，我把接入和落库拆成两个阶段：入口通过 Redis Lua 快速判断资格，成功后将订单消息发送到 Broker，消费者再按照数据库能承受的速度逐步落库。

当前生产端使用的是普通消息同步发送，不是事务消息。选择同步发送是因为 Redis 已经完成预扣，调用方需要知道 Broker 是否明确接收；如果发送抛出异常，就执行补偿 Lua，把用户从预扣集合移除、库存加回并删除预扣元数据。对于“Broker 可能收到但客户端超时”的未知结果，单靠即时补偿并不能完全证明一致，因此还保留预扣元数据，由后续对账任务检查订单是否真正落库。

消费端按“至少可能重复”设计，不能依赖 MQ 帮业务做到 Exactly Once。消费者先检查订单 ID，再检查用户和优惠券组合，并使用用户粒度锁处理并发消息，随后在数据库事务内条件扣库存和写订单。发生异常时不吞掉异常，让消息进入 RocketMQ 的重试流程。

选型上，Kafka 很适合高吞吐事件流、日志采集和数据管道，也支持幂等生产和事务，并不是不能做订单消息。但这个项目重点是业务消息、失败重试和延迟关单，RocketMQ 能在同一套设施中覆盖普通订单消息与延迟消息，所以综合业务匹配度和接入复杂度选择了 RocketMQ。

### 实际执行流程

```text
Lua 预扣成功
  → RocketMQ syncSend
  ├─ 明确失败：Lua 回滚 Redis 预扣
  └─ Broker 确认：接口返回订单 ID
       → SeckillOrderListener 消费
       → 幂等检查
       → MySQL 事务落库
       → 发送延迟关单消息
```

### RocketMQ 与其他方案比较

| 方案 | 更适合的场景 | 本项目取舍 |
|---|---|---|
| RocketMQ | 订单、交易等业务消息，重试、死信、延迟消息 | 当前采用，订单消息和延迟关单可以共用基础设施 |
| Kafka | 超高吞吐事件流、日志、数据管道、事件长期留存 | 能实现订单消息，但当前项目并不以流式分析为目标，延迟关单也需额外设计 |
| RabbitMQ | 复杂路由、中小规模业务消息 | 可以实现，但延迟通常依赖 TTL + DLX 或插件 |
| Redis Stream | 轻量消息流、较低部署成本 | 会与库存和缓存共享 Redis 资源，重试、死信和运维能力需要更多自建 |

### 高频追问

#### 追问 1：为什么不使用 RocketMQ 事务消息？

当前入口首先修改的是 Redis，而事务消息通常围绕本地数据库事务和消息发送设计。即使更换成事务消息 API，也需要可查询的本地事务状态或事务日志来回答回查。当前采用同步发送、明确失败回滚、预扣元数据和定时对账，更符合现有链路，但不能宣称使用了事务消息。

#### 追问 2：消息怎样保证不丢？

生产端等待 Broker 确认，明确失败时回滚；消费失败抛出异常触发重试；预扣元数据让对账任务能够发现长期未落库订单并使用原订单 ID 重投。生产部署还需要 Broker 高可用、磁盘持久化策略、消息轨迹、死信告警和容量监控。

#### 追问 3：为什么重投必须使用原订单 ID？

订单 ID 是第一层幂等键。如果补偿时生成新 ID，同一次业务预扣可能被修复成多笔订单；复用原 ID 后，多次重投仍然指向同一业务实体。

#### 追问 4：消息积压怎么办？

先区分生产速率过高还是消费异常，再检查数据库慢 SQL、连接池和消费者错误。可以增加消费实例和队列并行度，但扩容前要确认数据库承载能力，否则只是把 MQ 中的压力重新打到 MySQL。

#### 追问 5：这是不是 Exactly Once？

不是。项目按消息可能重复的前提设计，通过业务幂等使重复投递不产生重复业务结果，更准确的表述是“至少一次投递语义下的幂等消费”。

## 大问题三：你如何治理缓存击穿、缓存穿透，并使用 Redis GEO 完成附近商铺查询？

### 对应简历亮点

> 使用 Redis 逻辑过期与互斥锁解决热点店铺缓存击穿，并通过缓存空值降低缓存穿透风险；结合 Redis GEO 和 MySQL 实现附近商铺查询与详情补全。

### 面试官考察点

- 击穿、穿透、雪崩是否能区分；
- 逻辑过期为什么能保护数据库；
- 逻辑过期的可用性与一致性取舍；
- 当前接口缓存不存在时到底会不会回源；
- Redis GEO 与 MySQL 各自负责什么；
- Redis 5 与 GEOSEARCH 的兼容问题。

### 30 秒结论

热点店铺详情采用逻辑过期：Value 中保存业务数据和过期时间，逻辑过期后请求仍返回旧值，只有抢到互斥锁的线程异步查询 MySQL 重建缓存，从而避免热点 Key 失效时大量请求同时回源。缓存穿透通过短 TTL 空值缓存处理。附近商铺查询则由 Redis GEO 完成半径检索、距离计算和排序，再由 MySQL 根据 shopId 批量补充完整详情。

### 2～3 分钟完整口播

缓存治理需要先区分问题。缓存击穿是单个热点 Key 失效后大量请求同时回源；缓存穿透是持续查询缓存和数据库都不存在的数据；缓存雪崩是大量 Key 同时失效或者 Redis 整体不可用。

当前店铺详情属于读多写少的热点数据，我选择逻辑过期而不是等待式互斥锁。缓存中保存店铺数据和业务过期时间，未过期直接返回；已经过期时，当前请求仍然返回旧值，同时尝试获取店铺维度的 Redis 锁。只有抢到锁的线程进入缓存重建线程池，从 MySQL 查询最新数据并写回，其他线程不等待重建。这个方案用短时间旧数据换取高可用，适合商铺详情，不适合余额或实时库存。

缓存穿透方面，通用缓存组件还提供缓存空值方法：数据库查不到时写入短 TTL 空字符串，后续相同无效 ID 不再访问数据库。需要注意，当前 `/shop/{id}` 主路径实际使用逻辑过期，缓存 Key 不存在时直接返回空，因此压测前必须预热。击穿测试应该只把缓存对象内部 `expireTime` 改成过去时间，不能删除 Key。

附近商铺查询中，Redis GEO 只保存用于地理检索的店铺 ID 和坐标，根据用户位置查找五公里内商铺并按距离排序；然后 MySQL 按这些 ID 批量查询详情，并恢复 Redis 的排序。项目本地 Redis 是 5.0.14.1，所以将原来需要 Redis 6.2 的 GEOSEARCH 调整为兼容 Redis 5 的 GEORADIUS 调用。

### 逻辑过期流程

```text
读取 cache:shop:{id}
  ├─ Key 不存在：当前实现直接返回空
  └─ Key 存在：解析 data + expireTime
       ├─ 未过期：直接返回
       └─ 已过期：尝试获取 lock:shop:{id}
            ├─ 抢锁成功：提交异步任务查询 MySQL 并重建
            └─ 抢锁失败：不等待
       → 当前请求返回旧数据
```

### 为什么选择逻辑过期

| 方案 | 特点 | 本项目取舍 |
|---|---|---|
| 物理 TTL 直接失效 | 简单，但热点 Key 失效可能并发回源 | 不适合热点商铺 |
| 物理 TTL + 互斥锁 | 数据相对新，但未抢到锁的请求需要等待或重试 | 可用于更重视一致性的场景 |
| 逻辑过期 + 互斥重建 | 过期仍能返回，只有一个线程重建 | 当前热点店铺采用，优先保证可用性 |

### 高频追问

#### 追问 1：为什么逻辑过期 Key 不设置物理 TTL？

如果 Key 被物理删除，请求就无法取得旧数据，逻辑过期的“先返回旧值、后台重建”前提就不存在了。它通常依赖预热和长期保留 Key，再通过 Value 中的业务时间判断是否需要重建。

#### 追问 2：缓存重建线程执行失败怎么办？

当前代码会在 finally 中释放锁，但异常只在线程任务中抛出，没有完整重试和告警。生产化应增加线程池隔离、失败日志、监控告警以及重建重试策略。

#### 追问 3：为什么不用布隆过滤器解决穿透？

当前数据量和复杂度下，缓存空值实现简单且能精确表示某个 ID 不存在。布隆过滤器内存效率更高，适合海量固定集合，但存在误判以及数据新增、删除和同步维护成本。

#### 追问 4：Redis GEO 完全替代 MySQL 了吗？

没有。Redis GEO 负责附近 ID 检索、距离计算和排序；MySQL 仍然负责商铺完整字段和持久化数据查询。

#### 追问 5：GEO 数据如何初始化？

应将 `tb_shop.x`、`tb_shop.y` 按类型写入 `shop:geo:{typeId}`。坐标必须来自真实数据，不能为了压测随意填写，否则距离和排序没有验证意义。

## 大问题四：支付回调和超时关单同时到达时，如何保证订单状态与库存只变化一次？

### 对应简历亮点

> 使用 RocketMQ 延迟消息实现超时关单，基于乐观锁思想控制订单状态流转，解决支付回调与超时关单之间的并发竞争，并在关单后回补库存，保证订单与库存状态一致性。

### 面试官考察点

- 延迟关单为什么需要消息队列；
- 支付和关单竞争具体会产生什么错误；
- 条件更新为什么属于 CAS/乐观并发控制；
- 为什么必须检查受影响行数；
- 重复关单如何避免重复释放库存；
- 延迟消息与定时扫描的取舍。

### 30 秒结论

订单落库后发送 RocketMQ 延迟消息，到期后只尝试关闭仍为待支付状态的订单。支付回调执行 `待支付 → 已支付`，关单执行 `待支付 → 已取消`，两个操作都把旧状态作为更新条件，因此并发时只有一个更新能成功。只有关单状态更新成功后才回补 MySQL 库存，并通过 Lua 检查 Redis 预扣资格后释放一次，防止重复消息导致库存多加。

### 2～3 分钟完整口播

未支付订单如果长期占用库存，会导致库存资源无法重新销售。当前项目在订单消费落库成功后发送一条 RocketMQ 延迟消息，消息到期后由关单消费者处理。这里不直接无条件关闭订单，而是把订单仍处于待支付状态作为 SQL 更新条件。

支付回调和超时关单可能在同一时间到达。支付希望把状态从待支付改为已支付，关单希望从待支付改为已取消。如果双方都是先查询再无条件更新，就可能出现已付款订单被关闭，或者已经关闭的订单又被改成已支付。当前两个操作都通过 `WHERE id = ? AND status = 1` 更新，只有第一个成功修改状态的请求能影响一行，另一个请求影响行数为零并停止后续动作。

这个方案属于 CAS 式的乐观并发控制：更新时比较数据库当前状态是否仍等于预期旧值，满足才交换为新状态。它没有单独的 version 字段，所以准确描述应是“基于状态条件更新的乐观锁思想”，而不是说使用了 MyBatis-Plus 的版本号乐观锁插件。

只有订单成功从待支付变为已取消后，才把 MySQL 优惠券库存加一；随后执行 Redis 释放 Lua。脚本只有发现用户仍在预扣集合中才移除用户、库存加一并删除预扣元数据，因此重复延迟消息不会重复释放 Redis 库存。

### 状态竞争流程

```text
订单初始状态：待支付 status=1

支付回调：UPDATE ... SET status=2 WHERE id=? AND status=1
超时关单：UPDATE ... SET status=4 WHERE id=? AND status=1

先成功的一方影响 1 行
后到的一方影响 0 行并结束
```

### 为什么选择 RocketMQ 延迟消息

| 方案 | 优点 | 不足 | 本项目取舍 |
|---|---|---|---|
| 定时扫描订单表 | 实现简单 | 周期扫描数据库，时效取决于 Cron，多实例还要防重 | 不作为实时关单主方案 |
| Redis ZSet 延迟队列 | 时间灵活 | 轮询、抢占、重试和恢复都要自行实现 | 未采用 |
| RocketMQ 延迟消息 | 与订单消息共用设施，到期触发消费 | 4.x 延迟等级固定，时间精度有限 | 当前采用 |

### 高频追问

#### 追问 1：这算乐观锁吗？

它属于乐观并发控制思想，但不是传统 `version` 字段实现。这里直接使用业务状态作为比较值：只有状态仍为待支付时才允许更新。

#### 追问 2：为什么不能先查状态，再根据查询结果更新？

查询与更新之间存在并发窗口，两个线程都可能查到待支付。必须把状态判断写进同一条 UPDATE 的 WHERE 条件，由数据库原子决定竞争结果。

#### 追问 3：如果延迟消息重复投递呢？

第一次关单成功后状态已不是待支付，后续相同消息的条件更新影响行数为零，不会继续回补 MySQL；Redis 释放脚本也会检查用户是否仍在预扣集合，避免重复加库存。

#### 追问 4：RocketMQ 4.9.4 的延迟消息有什么限制？

当前版本使用预设延迟等级，不能为每一条消息指定任意精确时间。若业务要求任意时间点或超长周期关单，需要升级定时消息能力或采用专门的延迟任务服务。

### 压测证据

- 对同一待支付订单交错发送 50 次支付请求和 50 次关单请求；
- 最终只有一个状态条件更新成功；
- 该轮实验中关单获胜，订单状态为已取消；
- 数据库库存只回补一次。

### 不能夸大的边界

- 当前不是 version 字段乐观锁；
- 不能说延迟消息绝对只投递一次；
- RocketMQ 4.x 延迟等级不是任意精确时间；
- 状态竞争测试证明的是该轮并发正确性，不代表已经形式化证明全部故障路径。

## 大问题五：为什么还要引入 XXL-JOB，它如何完成对账、自动补偿和最终一致性修复？

### 对应简历亮点

> 基于 XXL-JOB 定时扫描 Redis 预扣元数据与 MySQL 订单状态，对未落库订单使用原订单 ID 重投 RocketMQ，对已取消订单幂等释放 Redis 预扣，并对异常任务进行失败重试。

### 面试官考察点

- 为什么实时补偿后仍需要定时对账；
- 对账任务以什么数据作为证据；
- 未落库、已落库、已取消分别怎么处理；
- 为什么重投复用原订单 ID；
- XXL-JOB 与 `@Scheduled`、Quartz、Redisson 锁如何选；
- 哪些能力已经实现，哪些仍待部署验证。

### 30 秒结论

实时发送失败补偿只能处理调用方明确知道的失败，无法覆盖进程宕机、发送结果未知、长期消费失败或人工误操作。因此 Lua 预扣时保存订单和用户的 reservation 元数据，XXL-JOB 周期扫描并与 MySQL 对账：未落库且超过等待窗口的订单使用原订单 ID 重投 RocketMQ；已落库订单修复用户集合并清理元数据；已取消订单通过 Lua 幂等释放 Redis 预扣。任务异常会抛给调度中心记录失败，并由 Admin 配置重试。

### 2～3 分钟完整口播

秒杀链路有即时补偿，但即时补偿只能处理程序明确捕获到的错误。例如同步发送直接抛出异常时，可以马上回滚 Redis；但如果应用在 Redis 预扣成功后突然宕机，或者 Broker 已经收到消息但客户端因网络超时无法确认，就可能留下 Redis 已预扣、MySQL 没有订单的中间状态。

为了解决这类未知异常，我在 Lua 预扣时额外写入 reservation 元数据，包括原订单 ID、用户、优惠券、预扣时间、重试次数和最近重试时间。XXL-JOB Admin 按 Cron 调度执行器中的 `seckillReconcileJob`，任务使用 SCAN 渐进式扫描这些记录，并查询 MySQL 订单状态。

如果数据库没有订单，而且预扣已经超过正常消费等待时间，任务使用原订单 ID 重新发送 RocketMQ；复用原 ID 可以继续利用消费端的订单幂等。如果订单已经落库，则修复 Redis 用户预占集合并清理 reservation；如果订单已经取消，则运行释放 Lua，移除用户并回补 Redis 库存。对于短时间刚产生的预扣不会立即重投，同时使用最近重试时间控制重投间隔，避免每次调度都重复发消息。

选择 XXL-JOB 而不是单纯 `@Scheduled`，主要是需要独立调度中心、执行记录、路由和失败重试。Redisson 锁只能解决多个实例谁执行，不能替代任务管理；Quartz 调度能力完整，但需要维护调度表和集群配置，对当前项目更重。当前代码、执行器和 JobHandler 已接入并通过编译，但 XXL-JOB Admin 的跨进程调度、故障转移和失败重试仍需实际部署后完成端到端验证。

### 对账分支

```text
XXL-JOB 触发 seckillReconcileJob
  → SCAN reservation 元数据
  → 查询 MySQL 订单
     ├─ 无订单且超过等待窗口：原订单 ID 重投 RocketMQ
     ├─ 订单已落库：修复 Redis 用户集合，清理 reservation
     └─ 订单已取消：Lua 幂等释放 Redis 预扣
  → 对比 Redis 活跃用户数与 MySQL 有效订单数
  → 异常向 XXL-JOB 抛出，由调度中心记录失败
```

### 为什么选择 XXL-JOB

| 方案 | 能解决什么 | 主要不足 | 本项目结论 |
|---|---|---|---|
| `@Scheduled` | 单机定时执行 | 缺少统一控制台、日志、路由和失败重试 | 不作为最终方案 |
| `@Scheduled` + Redisson | 多实例互斥执行 | 仍需自建任务管理、告警和重试 | 不采用 |
| Quartz | 持久化调度、集群和复杂触发器 | 调度表和集群配置较重，与业务应用耦合更深 | 当前场景不选 |
| XXL-JOB | 调度中心、执行器、日志、路由和失败重试 | 需要额外部署 Admin | 当前采用 |

### 高频追问

#### 追问 1：为什么不能只依赖 MQ 重试？

MQ 重试的前提是消息已经成功进入 Broker。若故障发生在 Redis 预扣之后、消息可靠进入 Broker 之前，单靠消费者重试看不到这笔预扣；对账任务通过 Redis reservation 主动发现这种孤立状态。

#### 追问 2：为什么重投不会创建重复订单？

重投复用原订单 ID，消费者先按订单 ID 幂等检查；同时还有用户券业务校验和用户锁。即使任务重复触发，多条消息仍指向同一个业务订单。

#### 追问 3：XXL-JOB 多实例会不会重复执行？

调度中心可以通过路由策略选择执行器，但业务补偿本身仍必须幂等，因为失败重试、故障转移和网络超时都可能造成重复触发。不能把调度层防重当作业务幂等。

#### 追问 4：为什么使用 SCAN，不使用 KEYS？

`KEYS` 会一次遍历整个 Key 空间，数据量大时可能长时间阻塞 Redis；`SCAN` 是渐进式遍历。生产数据继续增长后，还应建立按时间或券 ID 分片的待对账索引，避免长期全量扫描。

#### 追问 5：自动补偿能无限重试吗？

不能。应该设置最大重试次数、退避策略、告警和人工处理入口。当前代码记录 retryCount 和 lastRetryAt，并控制重投间隔，但还需要补充最大次数和异常表等生产化闭环。

## 大问题六：Redis + Lua + AOP 的滑动窗口限流是如何实现的，为什么选择它而不是固定窗口或令牌桶？

### 对应简历亮点

> 基于 Redis + Lua + AOP + 自定义注解实现滑动窗口限流，支持 IP 和用户维度，降低秒杀接口被恶意刷取和突发流量冲击的风险。

### 面试官考察点

- 为什么要在业务入口限流；
- AOP 和注解分别解决什么问题；
- Redis ZSet 如何表示滑动窗口；
- 多条 Redis 命令为什么还需要 Lua；
- 固定窗口、滑动窗口、令牌桶和漏桶如何选择；
- IP 限流、热点 Key、Redis 故障时的边界。

### 30 秒结论

接口通过 `@RateLimiter` 声明 Key、窗口、阈值和维度，AOP 在调用控制器前根据 IP、用户或全局维度生成 Redis Key。Lua 使用 ZSet 删除窗口外记录、统计当前请求数、判断是否达到阈值，并在允许时写入当前时间戳，整个过程原子执行。项目选择滑动窗口是因为它比固定窗口更准确，能够避免窗口边界瞬时通过双倍流量，同时 Redis 计数可以在多实例之间共享。

### 2～3 分钟完整口播

限流的目标不是解决库存超卖，而是在请求进入核心业务前控制恶意刷取和突发流量，避免大量请求同时占用线程、Redis 和下游资源。我把限流能力做成自定义注解，控制器只需要声明业务 Key、时间窗口、最大请求数和限流维度，AOP 切面统一完成身份解析和 Redis 判断，这样不会在每个接口复制限流代码。

具体算法使用 Redis ZSet。Score 保存请求时间戳，Member 使用时间戳加随机值区分同一毫秒的多个请求。每次请求先删除当前窗口之前的记录，再统计 ZSet 元素数量；如果已经达到阈值就拒绝，否则写入本次请求并设置过期时间。删除、计数和写入必须在同一个 Lua 中完成，否则多个实例并发时都可能在计数后认为自己可以通过，导致实际流量超过阈值。

当前店铺详情示例按 IP 限流，秒杀接口按用户限流，也支持全局 Key。相比固定窗口，滑动窗口不会在相邻窗口边界出现理论上的双倍突发；相比令牌桶，它的行为更容易解释，适合当前阈值不高的接口。代价是每个窗口内请求都要保存一个 ZSet 成员，高 QPS 和高基数维度下内存与 `O(logN)` 操作成本会增加。

### Lua 执行流程

```text
进入带 @RateLimiter 的接口
  → AOP 读取注解
  → 按 IP / 用户 / 全局维度生成限流 Key
  → Lua 删除窗口外 ZSet 成员
  → 统计窗口内请求数
  ├─ 已达到阈值：拒绝
  └─ 未达到阈值：写入本次时间戳并设置 TTL
  → 允许执行业务方法
```

### 限流算法比较

| 算法 | 优点 | 不足 | 本项目取舍 |
|---|---|---|---|
| 固定窗口 | 实现简单、内存低 | 窗口边界可能瞬间通过两倍流量 | 未采用 |
| 滑动窗口日志 | 时间范围准确、易解释 | 每次请求保存一条记录，内存成本较高 | 当前采用 |
| 滑动窗口计数 | 比日志法省内存 | 统计是近似值 | 高流量时可升级 |
| 令牌桶 | 可控制平均速率并允许一定突发 | 状态和补充令牌逻辑更复杂 | 网关流量治理更合适 |
| 漏桶 | 下游输出稳定 | 对突发请求主要表现为排队或拒绝 | 适合稳定消费速率场景 |

### 高频追问

#### 追问 1：为什么不用 Sentinel 或网关限流？

当前项目通过自定义方案展示滑动窗口原理，并支持用户与业务资源维度的细粒度限制。生产系统通常还会在网关或 Sentinel 做统一入口限流，业务层保留用户、优惠券等语义化规则，两层可以同时存在。

#### 追问 2：为什么 Redis 命令已经原子，还需要 Lua？

单条 Redis 命令原子不代表“删除旧记录 → 计数 → 判断 → 添加记录”这一组操作原子。若拆成多次网络请求，多个实例可能同时读到相同计数并一起放行。

#### 追问 3：按 IP 限流有什么风险？

多个用户可能通过 NAT 共用同一公网 IP；同时客户端可以伪造 `X-Forwarded-For`。生产环境只能信任受控代理写入的请求头，并在网关清洗外部伪造值，不能直接信任任意客户端 Header。

#### 追问 4：Redis 故障时应该放行还是拒绝？

当前代码在脚本返回空或零时拒绝，偏向保护系统。生产中需要按接口风险区分：秒杀等高风险写接口可失败关闭，普通查询可能允许降级放行或使用本地限流，避免 Redis 故障导致全部接口不可用。

#### 追问 5：滑动窗口的性能瓶颈是什么？

高基数用户和高 QPS 会产生大量 ZSet 成员，删除与插入都有排序成本。可以通过缩短窗口、限制维度数量、使用分桶计数、网关本地令牌桶或 Redis Cluster 分散 Key 来优化。

## 六题统一回答模板

任何一题都可以使用下面的顺序回答：

1. **场景：** 原链路在什么并发或故障情况下会出问题；
2. **目标：** 需要保护库存、数据库、缓存、订单状态还是流量入口；
3. **方案：** 使用了什么机制，各组件分别负责什么；
4. **流程：** 请求或消息从入口到最终结果经过哪些步骤；
5. **选型：** 还比较过哪些方案，为什么当前方案更合适；
6. **异常：** 发送失败、重复执行、并发竞争、宕机和积压如何处理；
7. **证据：** 使用什么压测、SQL、Redis 状态或消息指标验证；
8. **边界：** 当前没有实现什么，生产化还需要补什么。

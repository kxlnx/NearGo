# 本地压测摘要

测试日期：2026-09-18  
环境：Java 21.0.11、Spring Boot 2.7.4、本机 MySQL、Redis 5.0.14.1、RocketMQ 4.9.4 单 Broker。

以下结果用于验证功能正确性和观察单机性能，不外推为生产集群容量。

## Redis 5 GEO 兼容性

原实现通过 Spring Data Redis 发出 `GEOSEARCH`，在 Redis 5 环境下业务请求全部失败。切换为兼容的 `GEORADIUS` 后，仍由 Redis 完成附近商铺检索和距离排序，MySQL 根据商铺 ID 补充详情。

| 并发 | 原实现业务成功率 | 兼容版本业务成功率 | 成功请求 P95 | 有效 QPS |
|---:|---:|---:|---:|---:|
| 100 | 0% | 100% | 99.51 ms | 915.67 |
| 500 | 0% | 100% | 19.41 ms | 4258.65 |
| 1000 | 0% | 100% | 33.08 ms | 4520.89 |

失败请求的低耗时不代表性能更好，因此这里只把结果描述为兼容性和可用性修复。

## 热点店铺逻辑过期

预热 `cache:shop:1` 后，只将 RedisData 内部 `expireTime` 修改为过去时间，不删除缓存 Key，再发起 100 并发访问：

| 请求数 | 业务成功 | HTTP/传输错误 | P95 | P99 |
|---:|---:|---:|---:|---:|
| 100 | 100 | 0 | 9.28 ms | 9.35 ms |

该实验验证了“返回旧值并异步重建”的接口行为。由于 MySQL 指标来自实例级全局计数，本报告不声称数据库恰好只执行了一次查询。

## 1000 用户抢 100 件库存

| 请求数 | 进入 RocketMQ | 库存不足 | DB 订单数 | 重复用户券订单 | P95 | QPS |
|---:|---:|---:|---:|---:|---:|---:|
| 1000 | 100 | 900 | 100 | 0 | 1462.68 ms | 593.06 |

消费完成后：

```text
Redis 初始库存 100 = Redis 剩余库存 0 + Redis 用户集合 100
MySQL 初始库存 100 = MySQL 剩余库存 0 + 有效订单 100
```

## 重复请求

| 场景 | 请求 | 成功 | 业务拒绝 | DB 订单 | 重复用户券订单 |
|---|---:|---:|---:|---:|---:|
| 同一用户重复请求 | 5 | 1 | 4 | 1 | 0 |
| 10 个用户混合重复 | 50 | 10 | 40 | 10 | 0 |

## RocketMQ 积压恢复

关闭消费者后，100 条通过 Redis 资格校验的消息进入 RocketMQ，数据库订单保持为 0。恢复消费者并重启应用后，100 条订单全部落库，消费组差值恢复为 0；从消费者启动到订单追平约 13.5 秒。

## 支付与关单竞争

对同一待支付订单交错发送 50 次支付请求和 50 次关单请求，只有一个状态条件更新成功；该轮测试中关单获胜，订单最终状态为已取消，数据库库存只回补一次。

## 数据边界

- 所有结果来自本地单机短时突发压测。
- 查询接口受到缓存热度、连接池状态和测试顺序影响，不据此计算统一的性能提升百分比。
- 秒杀业务拒绝不计为 HTTP 或传输错误。
- 仓库仅保存脱敏后的汇总数据，不上传登录 Token、个人信息和大体积逐请求原始文件。

## 3. 发现的四个问题

### 问题 1：缓存击穿（🔴 高）

**现象**：缓存失效瞬间，并发请求全部穿透到 MySQL 做同一件事。

**根因**：`VoucherServiceImpl` 两条路径用的是**朴素 Cache-Aside，没有任何并发合并**：

```java
// 修复前
List<Voucher> local = localVoucherCache.getIfPresent(shopId);  // ① 查 L1
if (local != null) return ...;                                 // ② 空
String cached = stringRedisTemplate.opsForValue().get(redisKey);// ③ 查 L2
if (cached != null) return ...;                                // ④ 空
List<Voucher> vouchers = getBaseMapper().queryVoucherOfShop(shopId); // ⑤ 全部冲到这里
```

**两个条件同时成立才会击穿**：

| 条件 | 说明 |
|---|---|
| **A. 缓存同时失效** | Redis key 有 30s TTL，到点整个 key 一起消失 → 所有并发请求在同一瞬间看到"空" |
| **B. 判空后没有合并** | 每个线程各自往下查库 → N 个并发 = N 次同样的查询 |

**日志铁证**：`06:55:54.234` 同一毫秒内 12 个线程执行同一条 SQL：

```
[io-8081-exec-18]  queryVoucherOfShop : ==> Preparing: SELECT ...
[io-8081-exec-84]  queryVoucherOfShop : ==> Preparing: SELECT ...
[io-8081-exec-86]  queryVoucherOfShop : ==> Preparing: SELECT ...
[io-8081-exec-88]  queryVoucherOfShop : ==> Preparing: SELECT ...
... 12+ 个线程在同一毫秒
```

**为什么店铺详情没有这个问题**：它走 `CacheClient.queryWithLogicalExpire` —— key 物理永不过期（24h 兜底）所以**从根本上不存在"同时看到空"**，再叠加互斥令牌，100 并发只回源 2 次。

**放大效应**：击穿是**每实例**行为，N 个实例同时遇到 L2 过期 → N × 11 次并发查询砸向 MySQL。

### 问题 2：L1 没有失效广播，跨实例最多 5 秒不一致（🟡 中）

- 代码注释自认："详情数据几乎不变，用短 TTL 收敛一致性（**不做跨实例失效广播**）"
- 影响：A 实例重建缓存后，B 实例的 Caffeine 最多 5 秒仍在返回旧数据
- **能力已有但未接上**：优化九的 `SeckillSwitchCacheSync` 就是一套 Redis Pub/Sub 失效广播，可直接复用

### 问题 3：库存字段会「静默降级」（🟠 中高）

```java
// 修复前
String liveStock = stringRedisTemplate.opsForValue().get(SECKILL_STOCK_KEY + dto.getId());
if (liveStock != null) {              // ← Redis 读不到时什么都不做
    dto.setStock(Integer.valueOf(liveStock));
}
```

Redis 库存 key 丢失时，详情页**不报错**，静默使用 MySQL 里的库存快照 → 用户看到"详情页有货、点进秒杀却提示**库存未初始化**"。

**本次压测真实触发过**：机器休眠后 Redis 重启，`seckill:stock:*` 全部丢失，正好走的就是这条路径。

### 问题 4：券列表 L1 过期后第一波 200 并发卡 ~2.8 秒（🟠 中高，未定位）

| 端点 | 场景（L1 过期、L2 有效、200 并发） | 首波耗时 |
|---|---|---|
| 券详情 | | **17 ms** ✅ |
| **券列表** | | **~2800 ms** ❌（两次独立运行均复现） |

**已排除**：不是 MySQL —— 日志证明 `queryVoucherOfShop` 本身只要 **2~3ms**（`Preparing` .234 → `Total` .236）。

**未定位**：疑似 L1 同时失效瞬间 200 个请求争抢 Redis 连接（Lettuce 池 `max-active=10`）或线程调度；但券详情每请求也读 Redis 却无此现象，**故不给出未经证实的结论**。下一步需在停顿瞬间抓线程栈 / 打开连接池监控。

## 4. 修复内容

### 4.1 改动清单

| 文件 | 改动 |
|---|---|
| `VoucherServiceImpl.java` | 两条路径改用 **Caffeine `get(key, loader)` 单飞**；增加 Redis 故障降级；库存降级改为**留痕告警**；空列表返回哨兵值而非 null |
| `CacheClient.java` | 重建令牌升级为**带持有者标识（UUID）**；释放走 **Lua 原子「比对+删除」**；增加**有界等待**（3×20ms）与 **Redis 故障降级** |

### 4.2 核心：`Caffeine#get(key, loader)` 单飞

```java
// 修复后
List<Voucher> vouchers = localVoucherCache.get(shopId, this::loadVoucherList);
// get(key, loader) 语义：同一个 key 的并发请求只会有一个线程执行 loader，
// 其余线程等它的结果 —— 从根上消除「判空后各自查库」
```

**一个必须注意的坑**：Caffeine **不缓存 null**。loader 返回 null 会让每个请求都重新加载，等于没缓存。因此券列表返回**空集合哨兵**而不是 null。

### 4.3 令牌语义升级（针对"会不会超时 / 会不会误删别人的令牌"）

```java
// ① 抢令牌时带上持有者标识
String token = UUID.randomUUID().toString();
Boolean ok = stringRedisTemplate.opsForValue()
        .setIfAbsent(lockKey, token, LOCK_SHOP_TTL, TimeUnit.SECONDS);

// ② 释放时只删自己的 —— 比对+删除必须合成一条原子命令
private static final DefaultRedisScript<Long> UNLOCK_SCRIPT = new DefaultRedisScript<>(
    "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end",
    Long.class);
```

**为什么必须用 Lua**：`if (get(key).equals(token)) delete(key)` 是两条命令，两步之间令牌可能刚好过期并被别人抢到，仍然会误删别人的令牌。

**为什么不需要 watchdog 续期**：令牌 TTL 应 ≥ 重建 P99 的 10 倍。实测重建耗时：券列表 **54ms**、券详情 **3ms**，TTL 10 秒 = 重建时间的 **185~3000 倍**，续期在这个场景没有意义。

**为什么不用 Redisson**：

| Redisson 能力 | 缓存重建是否需要 |
|---|---|
| 持有者标识 + Lua 原子解锁 | ⚠️ 需要 → **5 行代码即可自实现**（项目已有 `SimpleRedisLock`） |
| watchdog 自动续期 | ❌ 不需要（TTL 已是重建耗时的 185 倍） |
| 可重入 | ❌ 不需要 |
| **Pub/Sub 排队唤醒** | ❌ **有害**：让读请求排队等待，在秒杀场景会打满 Tomcat 线程池 |

**关键区分**：这里用 `setIfAbsent` 是当**"重建权令牌"**而不是锁 —— 抢不到**不排队、不等待，直接返回旧值**。

### 4.4 有界等待 + 降级

```java
// 没抢到令牌：最多等 3×20ms，超时自己回源（有上限，不会雪崩）
for (int i = 0; i < REBUILD_WAIT_RETRY; i++) {
    sleepQuietly(REBUILD_WAIT_INTERVAL_MS);
    String again = safeGet(key);
    if (again != null) return parse(again, type);
}
```

```java
// Redis 不可用：降级直查数据库，不让缓存层故障传染成业务故障
try { json = stringRedisTemplate.opsForValue().get(key); }
catch (Exception e) { log.warn("[缓存降级] ...", e); return dbFallback.apply(id); }
```

### 4.5 修复范围的诚实说明

| 路径 | 本次修复 |
|---|---|
| 券列表 / 券详情 | **进程内单飞**（Caffeine），把本实例并发合并为 1 次加载 |
| 店铺详情 | 走 `CacheClient.queryWithLogicalExpire`，**本次升级了它的令牌语义 + 有界等待 + 降级** |
| 跨实例合并 | 若需把 N 个实例的 1 次也合并成全局 1 次，把两条券路径改走 `cacheClient.queryWithLogicalExpire` 即可（能力已就绪） |

**当前取舍**：10 个实例最多 10 次并发回源，而回源只要 3~54ms，MySQL 完全无压力 → 不为此引入跨实例令牌的复杂度。

## 5. 修复后复测

### 5.1 击穿是否消除（关键指标：回源次数应与并发量无关）

| 场景 | 修复前 | 修复后 | 结论 |
|---|---|---|---|
| 券列表 · 20 并发全冷 | 11 次回源 | **1 次** | ✅ |
| 券列表 · 200 并发全冷 | 7 次回源 | **1 次** | ✅ |
| 券详情 · 20 并发全冷 | 11 次回源 | **1 次**（2 条 SQL） | ✅ |
| 券详情 · 200 并发全冷 | 8 次回源 | **1 次**（2 条 SQL） | ✅ |

**决定性证据：修复后 20 并发与 200 并发结果完全相同（都是 1 次回源）** —— 并发量不再是回源次数的因子，这就是单飞的定义。

### 5.2 热路径性能无退化

| 端点 | 修复前 QPS / p50 | 修复后 QPS / p50 |
|---|---|---|
| 券列表 | 8912.7 / 14 ms | **7949.1 / 17 ms** |
| 券详情 | 10548.5 / 13 ms | **9398.5 / 15 ms** |

差异约 11%，来自进程重启后 JIT 冷启动与机器状态波动，**同一量级，无结构性退化**。

### 5.3 冷启动的代价

修复后，抢先拿到加载权的线程要等一次回源（券列表 54ms、券详情 3ms），**其余并发请求等它**（而不是一起压库）。这是刻意的取舍：

```
用「一次可控的等待（≤54ms）」换掉「N 次数据库查询」
```

## 6. 结论与后续

### 结论

1. **多级缓存有效**：L1 命中 7949~9398 QPS，5000 请求回源 ≈ 0 次。
2. **但失效路径缺防护**：两条券路径是朴素 Cache-Aside，两级同时失效时发生击穿（11 次回源）。
3. **修复后击穿消除**：回源次数 11 → 1，且**与并发量无关**（20 并发与 200 并发结果相同）。
4. **令牌的两个担心（超时 / 误删）已从语义上解决**：UUID 持有者标识 + Lua 原子释放；且 TTL 是重建耗时的 185~3000 倍，超时在实际中不会触发。
5. **不需要 Redisson**：缓存重建是幂等操作，弱原语足够；分布式锁的排队语义在读路径上有害。
